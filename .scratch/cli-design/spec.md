# Yoho CLI 首个里程碑：本地博客文章管理

Status: ready-for-agent

## Problem Statement

用户需要通过终端管理现有博客文章，也需要让自己的本地产品以结构化参数调用同一套操作。目前项目只有探索文档，没有可安装的 CLI，命令行为、输出协议和内容保护规则需要形成可实现的规格。

现有博客已有文章格式、文章标识和内容加载规则。CLI 编辑后的文章必须继续被博客正确读取，并保留作者、日期、图片引用及其他现有信息。首个里程碑通过列出文章、查看文章和修改标题验证完整流程。

## Solution

提供可本地安装的 `yoho` 命令，使用 `yoho blog` 命令组管理现有博客的本地文章。用户可以列出全部状态的文章、查看完整内容，并按文章标识修改标题。

命令同时提供终端文本和 JSON 输出。参数完整时，命令无需交互。本地产品负责对话和模型调用，CLI 负责执行明确的操作。

首个里程碑在 macOS 上验收。通过安装后的真实命令验证结果，并使用博客现有内容加载逻辑验证编辑后的兼容性。

## User Stories

首个里程碑覆盖以下使用场景。

1. 作为博客作者，我希望安装本地 npm 包后获得 `yoho` 命令，以便直接在终端管理文章。
2. 作为博客作者，我希望在博客项目内运行命令时自动定位项目根目录，以便减少重复指定路径。
3. 作为本地产品的调用方，我希望通过参数指定博客项目，以便从任意工作目录执行操作。
4. 作为博客作者，我希望项目无法定位时收到明确错误，以便修正调用位置或目标路径。
5. 作为博客作者，我希望列表显示文章标识、标题、状态和发布日期，以便找到需要处理的文章。
6. 作为博客作者，我希望列表默认包含草稿、已发布和已归档文章，以便管理网站尚未公开展示的内容。
7. 作为博客作者，我希望按文章状态筛选列表，以便集中处理某个阶段的文章。
8. 作为博客作者，我希望文章按发布日期倒序排列，同日按文章标识排序，以便获得稳定的查找顺序。
9. 作为博客作者，我希望通过包含子目录的文章标识定位文章，以便保留既有内容组织方式。
10. 作为博客作者，我希望管理现有 Markdown 和 MDX 文章，以便沿用博客已支持的内容格式。
11. 作为博客作者，我希望修改标题时文章标识、文件名和访问地址保持不变，以便保留已有链接。
12. 作为博客作者，我希望查看文章时获得完整正文，以便核对内容后再编辑。
13. 作为本地产品的调用方，我希望查看结果包含全部元数据，以便保留博客已有字段及扩展信息。
14. 作为博客作者，我希望查看结果保留原始图片引用，以便了解文件中实际保存的内容。
15. 作为博客作者，我希望查看结果包含文章文件位置，以便定位原始文件。
16. 作为博客作者，我希望明确指定新标题，以便完成一次范围清晰的编辑。
17. 作为博客作者，我希望标题修改只影响元数据中的标题，以便保留正文中的同名标题。
18. 作为博客作者，我希望修改标题后正文保持原样，以便避免编辑无关内容。
19. 作为博客作者，我希望修改标题后其他元数据及未知字段保持原样，以便保留作者、日期和站点扩展信息。
20. 作为博客作者，我希望修改标题后注释、排版和图片引用保持原样，以便避免无关的文件差异。
21. 作为博客作者，我希望标题修改不自动更新文章更新时间，以便保留既有的时间记录规则。
22. 作为博客作者，我希望新标题支持中文和引号等正常字符，以便使用自然的文章标题。
23. 作为博客作者，我希望新标题去除首尾空白，以便避免意外空格进入标题。
24. 作为博客作者，我希望空白或多行标题被拒绝，以便及时修正无效输入。
25. 作为博客作者，我希望新标题与原标题相同时不写文件，以便避免无意义的修改。
26. 作为本地产品的调用方，我希望查看结果包含文章版本，以便在更新时说明自己依据的内容状态。
27. 作为本地产品的调用方，我希望基于旧版本的条件更新被拒绝，以便在冲突后重新读取文章。
28. 作为博客作者，我希望未指定版本时基于当前文件修改标题，以便直接完成终端编辑。
29. 作为博客作者，我希望写入失败时原文件保持完好，以便继续使用现有文章。
30. 作为博客作者，我希望列表遇到损坏文章时报告具体文件并失败，以便发现数据问题。
31. 作为博客作者，我希望查看和修改单篇文章只检查目标文章，以便其他文章的问题不阻断当前操作。
32. 作为博客作者，我希望文章不存在时收到明确错误，以便修正文章标识。
33. 作为博客作者，我希望同一文章标识对应多个文件时收到歧义错误，以便先解决重复内容。
34. 作为博客作者，我希望文章标识只能访问文章目录内的文件，以便约束编辑范围。
35. 作为博客作者，我希望默认输出清晰的终端文本，以便直接阅读操作结果。
36. 作为本地产品的调用方，我希望 JSON 模式成功时返回结构化结果，以便继续处理列表、文章或修改信息。
37. 作为本地产品的调用方，我希望 JSON 模式失败时也返回结构化结果，以便使用同一读取方式处理失败。
38. 作为本地产品的调用方，我希望诊断日志与 JSON 结果分开，以便稳定解析结果。
39. 作为本地产品的调用方，我希望完整参数的调用无需交互，以便自动执行操作。
40. 作为本地产品的调用方，我希望通过退出码区分参数、文章数据、权限和文件读写错误，以便决定后续处理方式。
41. 作为终端用户，我希望取消操作时获得约定的取消退出码，以便识别调用被中断。
42. 作为本地产品的调用方，我希望错误包含稳定的字符串错误码和可读说明，以便分别支持程序判断和用户提示。
43. 作为博客作者，我希望修改后的文章仍被博客实际内容加载逻辑正确读取，以便信任 CLI 的编辑结果。
44. 作为博客作者，我希望在 macOS 上验证安装后的命令，以便确认交付物能在自己的环境中使用。
45. 作为博客作者，我希望写入测试使用临时文章副本，以便验收过程不改动真实文章。

## Implementation Decisions

### 产品与模块边界

- CLI 使用 TypeScript、Node.js、pnpm、Commander 和 Zod，采用单包分层结构。
- 命令适配器负责参数转换、输入校验和调用文章服务。文章服务负责列出、查看及修改标题的业务规则。文件适配器负责定位、解析和写入文章，输出适配器负责文本、JSON 及退出码。
- 业务逻辑不依赖终端渲染或模型 SDK。CLI 执行确定性操作，对话、模型调用和会话管理属于外部本地产品。
- 首个管理对象是现有博客的本地文章。沿用其内容契约，不要求迁移元数据格式。

### 命令与项目定位

- 可执行命令名为 `yoho`，博客命令组为 `yoho blog`，提供 `list`、`show` 和 `update`。
- 查看与更新通过文章标识定位目标，更新通过 `--title` 接收标题。JSON 输出通过 `--json` 选择，条件更新通过 `--if-match` 指定文章版本。
- 在博客项目内运行时自动定位项目根目录。调用方可通过 `--project` 显式指定项目。无法定位目标时明确失败。
- 参数完整时无需交互。首个里程碑不增加全局项目绑定。

### 文章标识与读取

- 文章标识沿用博客现有规则，由文章相对于内容目录的路径去掉 Markdown 或 MDX 扩展名得到，保留子目录。
- 元数据校验沿用站点现有契约。标题和描述为字符串，发布日期必须可解析为有效日期。状态默认为草稿，草稿标记默认为 false，语言默认为中文，标签默认为空列表。读取时的默认值不要求回写原文件。
- 修改标题不改变文件名、文章标识或访问地址。
- 列表默认包含草稿、已发布和已归档文章，支持按状态筛选。文章状态与网站公开可见性保持区分。
- 列表结果包含文章标识、标题、状态和发布日期。按发布日期倒序排列，同日按文章标识排序。
- 查看结果包含完整正文、全部元数据、文件位置和文章版本。正文和图片引用保持文件中保存的含义，不执行站点展示转换。
- 列表遇到损坏文章时失败，并指出具体文件。查看或修改单篇文章只检查目标文章。

### 标题更新与内容保护

- 新标题去除首尾空白后必须是非空单行文本，支持中文、引号等正常字符。
- 更新严格只修改文章元数据的标题字段，保留正文、其他元数据、未知字段、日期、图片引用、注释和排版。
- 更新不自动修改文章更新时间，也不修改正文中的同名标题。
- 新标题与原标题相同时不写入文件，并在结果中明确没有实际修改。
- 更新结果包含文章标识、新标题、修改后的文章版本和是否实际发生修改。
- 查看返回的文章版本用于条件更新。指定版本与当前版本不符时，拒绝修改。未指定版本时，基于当前文件修改标题并保留其他内容。
- 文章标识必须指向文章目录内的文件。同一文章标识同时对应 Markdown 与 MDX 文件时，报告歧义。
- 参数错误、标题不合法、文件存在歧义或写入失败时，保留原文件。写入过程不得留下半写入文章。

### 输出与错误契约

- 默认输出面向人的文本。JSON 模式下，每次成功或失败都在 stdout 输出一个 JSON 结果，stderr 只输出诊断日志。
- 成功结果包含值为 true 的 `ok` 和承载业务结果的 `data`。
- 失败结果包含值为 false 的 `ok` 和 `error`。错误对象包含稳定的字符串 `code` 和面向人的 `message`，不存在文章的错误码为 `ARTICLE_NOT_FOUND`。
- JSON 结果和退出码共同构成调用契约，失败使用非零退出码。

| 退出码 | 含义 |
| --- | --- |
| 0 | 成功 |
| 2 | 参数错误 |
| 3 | 文章数据错误或版本冲突 |
| 4 | 权限错误 |
| 5 | 文件读写失败 |
| 130 | 用户取消 |

### 本地交付

- 构建可本地安装的 npm 包，验收安装后实际可执行的 `yoho` 命令。
- 首个里程碑以 macOS 为验收平台，实现采用跨平台接口。

## Testing Decisions

### 主要测试边界

- 以本地 npm 包安装后的 CLI 子进程为主要测试边界。测试提供工作目录、命令参数和临时文章目录，观察 stdout、stderr、退出码及文件结果。
- 该边界覆盖参数处理、项目定位、文章服务、文件适配器和输出适配器。优先通过真实命令验证整体行为，避免为每个内部函数建立重复测试。
- 用户已在前序 Q21 确认此边界，并确认以博客实际内容加载逻辑验证编辑兼容性。本规格沿用该决定。

### 测试质量与既有依据

- 好的测试描述使用者可观察的结果，不依赖内部函数名称、模块调用顺序或特定库的实现方式。
- 本仓库尚无实现代码和测试。关联博客已有本地文章加载测试，覆盖真实内容读取、状态过滤、子目录文章标识、日期及图片处理。这些测试提供兼容性验证的既有依据。
- 博客内容加载逻辑是编辑兼容性的验收依据。验收显式使用本地内容模式，避免 PageHush 模式干扰结果。
- 所有写入测试使用临时文章副本。测试前后比较实际文件，验证标题之外的内容保持原样。相同标题场景还验证没有触发写入。

### 必须覆盖的外部行为

1. 构建并安装本地 npm 包，从安装位置运行三条业务命令。
2. 从博客项目根目录及子目录定位项目，从其他目录显式指定项目，并验证无法定位项目时的错误。
3. 默认列出全部状态，验证状态筛选、发布日期倒序和同日文章标识排序。
4. 查看包含子目录的文章标识，读取完整正文、全部元数据、文件位置和文章版本。
5. 修改含中文或引号的标题，验证首尾空白处理，以及空白、多行或缺失标题被拒绝。
6. 修改标题后验证文件名、文章标识、正文、未知字段、作者、日期、图片引用、注释和排版保持原样。
7. 通过博客实际内容加载逻辑读取修改后的文章，确认新标题生效。
8. 重复提交相同标题，确认结果表示没有修改且文件没有被重写。
9. 先查看，再改变文章，使用旧文章版本更新时确认发生冲突且文件保持当前内容。使用当前版本更新时确认成功。
10. 不指定文章版本时，确认更新基于当前文件，并保留其中其他内容。
11. 列表遇到损坏文章时失败并指出具体文件。其他文章损坏时，查看或更新一个正常目标仍按目标文章处理。
12. 验证不存在的文章、重复文章标识、路径越界、权限错误和文件读写失败的结果，并检查修改失败时原文件完好。
13. 检查文本可读性。检查 JSON 成功与失败结果均可从 stdout 单独解析，诊断信息不污染结果，退出码符合约定。
14. 验证参数完整的调用无需交互，并验证取消时的退出码。

上述行为全部通过后，首个里程碑才算完成。测试不得依赖新增文章、删除文章或公开发布流程。

## Out of Scope

- 新建、删除、归档或发布文章，以及修改正文、标签、日期等其他字段。
- PageHush 数据同步、后台 API 接入和线上站点部署。
- 自动 Git 提交、推送或自动触发站点发布。
- Skill 安装、更新、校验、移除和分发。后续管理命令使用 `yoho skill` 命令组。
- CLI 内置聊天、模型调用、会话管理、完整 AI 对话接入和 Tool Registry 接入。
- MCP Server、第三方插件体系、TUI、Web 控制台和完整 Skill Registry。
- 全局项目绑定、多包拆分、公开 npm 发布和单文件二进制分发。
- Linux 和 Windows 的安装验收。
