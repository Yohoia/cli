# 远程博客管理访谈

Status: ready-for-agent

## 已确认的方向

- Q1：CLI 直接调用远程内容 API 执行文章管理，以服务器返回结果为准，不引入本地文章与远程文章的双向同步。
- Q2：后续目标不保留现有本地文章管理模式，集中完善远程管理。
- Q3：允许配套修改 PageHush 后端与授权页面，补齐设备授权、服务器端原子版本保护和创建请求去重。
- Q4：用户限定首个远程版本为展示文章列表、查看文章详情、发布文章、删除文章和增加文章。不额外纳入已有文章正文编辑、标签与主题管理或独立素材管理命令；新增使用本地 Markdown 文件路径，并可在文章上传流程中处理正文引用的本地图片。
- Q5：采用 OAuth 设备码授权；CLI 显示短码，用户在 PageHush 网页完成登录和授权确认，CLI 获取设备令牌。未选择浏览器回调加 PKCE 或 PAT 作为本期登录方案。
- Q6：新增与发布分离。新增文章先保存为草稿，发布使用独立操作，具体发布行为见 Q12。
- Q7：采用软删除。删除设置 `deleted_at`，正常列表和博客读取隐藏文章，但保留数据库记录及素材；本期没有恢复接口。CLI 应提供删除预览，并要求使用 `--yes` 显式执行。
- Q8：操作目标使用远程文章标识，支持服务器 UUID 和短 ID；标题与可变 slug 不作为权威身份。
- Q9：网页与 CLI 共同使用服务器端文章版本保护。并发冲突必须明确失败，不覆盖较新的文章；网页需要保留用户尚未保存的输入。保护必须由服务器原子执行，不能只依赖 CLI 先读后比较。
- Q10：设备授权默认有效 30 天，过期后重新登录。执行 CLI 注销命令时撤销当前授权；PageHush 网页提供设备授权查看和撤销能力。此处退出指 `logout`，不是每条 CLI 命令进程结束。
- Q11：用户将新增输入改为本地 `.md` 文档的路径，由 CLI 读取文档并上传为远程草稿，而非通过 `--body` 或 `--body-file` 拼装文章。字段提取、重复执行和图片引用行为已在 Q21–Q23 确认；早期 Q11 中整组字段建议没有全部接受。
- Q12：发布使用 `yoho blog publish <id>`。首次发布由服务器记录发布时间；重复发布返回已发布且未修改，保持日期和文章版本不变。
- Q13：`--dry-run` 返回文章标题、状态与版本。实际软删除要求同时提供 `--yes` 和 `--if-match <版本>`；文章在预览后变化时明确失败，要求重新查看。
- Q14：读取请求有限重试；写入通过服务端请求标识避免重复执行。超时后先查询结果，无法确认时明确报告结果未知并提供查询方式。
- Q15：默认服务地址为 `https://pagehush.yohoia.cn`，支持 `--server` 与环境变量覆盖；本期只配置一个默认服务，不增加多套 profile。
- Q16：服务器将 CLI 设备令牌限制为列出、查看、创建草稿、发布、软删除文章，以及创建文章时上传正文内嵌图片的窄权限；不授予修改已有正文、独立管理素材、标签或主题的权限。
- Q17：令牌按服务地址隔离，优先保存于系统凭据存储；不可用时明确报错。脚本可通过环境变量提供有效设备令牌，环境变量令牌不落盘。
- Q18：列表支持状态筛选、关键词搜索和分页，默认每页 20 篇；详情返回完整正文。沿用默认文本输出与 `--json`，保留现有退出码和诊断日志约定。
- Q19：PageHush 网页与后端一同升级。升级后，修改、发布、删除请求必须携带版本条件，缺少条件的旧请求明确失败；现有剪藏扩展创建草稿的接口保持兼容，新 CLI 创建请求必须支持去重。
- Q20：使用安装后的 CLI、临时 PageHush API 和隔离数据库验收；真实并发冲突使用临时 PostgreSQL 验证。本轮验收不写入线上文章。
- Q21：新增命令按 `yoho blog create <path-to-md>` 设计，支持普通 Markdown 和带 YAML frontmatter 的 Markdown。标题依次取 `title`、正文首个一级标题、文件名；读取 `description` 和 `language`，缺少描述时自动生成摘要，语言默认中文；去除 frontmatter 后正文保持原样，例外是按 Q22 在提交副本中改写本地图片引用；其他字段提示未导入，结果始终为草稿。
- Q23：每次主动执行 `create` 都表示新增文章，同一次上传的网络重试复用请求编号以防重复创建；修改本地文件后重新执行不会自动覆盖已有远程文章。
- Q24：CLI 保存服务地址、请求编号、文件指纹等最少操作记录以查询结果，不保存正文；服务端至少保留 7 天操作结果，超过期限且仍无法确认时提示人工检查。
- Q25：登录显示授权网址和设备码并尝试打开浏览器；取消或超时明确退出。`logout` 撤销当前授权，撤销失败时保留凭据供重试。
- Q26：发布要求调用方提供查看文章时取得的版本，即 `yoho blog publish <id> --if-match <revision>`；服务器统一检查标题、正文、描述非空，文章变化时拒绝发布并要求重新查看。
- Q22：确认自动处理 Markdown 正文引用的本地行内图片。CLI 以 `.md` 文件目录解析路径，通过 PageHush 素材 API 上传 `inline_image`，由服务端写入 MinIO；不向 CLI 下发 MinIO 密钥。CLI 只在内存副本中将本地路径改写为稳定素材地址，源文件保持不变。支持 JPEG、PNG、WebP，单张不超过 5 MiB；远程地址和已有 PageHush 素材地址保留；本地附件、其他 Markdown 文档链接和不支持/缺失/上传失败的图片不允许创建文章。重复引用同一图片只上传一次；文章创建失败时由服务端在至少 7 天后清理未被引用素材。该流程需要素材上传幂等、未引用素材清理和专用窄权限。
- Q27：空正文在任何远程上传前拒绝，包括只有 frontmatter、正文为空白的文件，避免创建本期无法通过 CLI 补齐正文或发布的草稿。
- 本文是访谈记录，不是可执行规格。当前 CLI 0.2.0 仍管理本地文章；本轮没有修改 CLI 或后端实现，也没有访问线上服务。

## 已核对的本地源码事实

- 已找到相邻 PageHush 后端。现有博客的 PageHush 模式直接读取其文章数据库。用户称服务为 Page；后续讨论按现有博客接入对应的 PageHush 项目核对，生产服务版本尚未验证。
- 文章 API 已支持列表、新建、查看、部分更新和删除，另有素材上传能力。文章管理需要有效登录会话，可通过无 Cookie 登录接口取得会话令牌。
- 当前身份模型为单作者访问码与会话，没有现成的 OAuth 设备授权、PAT、权限范围管理或设备令牌列表。已有网页只支持登录与退出当前会话；更换为标准设备授权需要配套增加后端流程和网页确认页面。
- 远程文章的稳定身份为 UUID，另有短地址和可读地址。历史本地相对路径标识不能直接作为远程文章身份使用。
- 远程文章状态只有草稿和已发布，没有已归档；删除是软删除，不移除数据库行与素材对象，未找到恢复接口。
- 当前后端没有文章原子版本前置条件，也没有创建幂等键。客户端先读后比较不能保证网页与 CLI 并发编辑时不互相覆盖；网络中断后盲目重试创建可能产生重复文章。
- 远程字段校验、日期更新和发布规则与本地模式不同，应以远程内容契约为准，不能直接复制本地语义。
- 新增 API 结构上只要求标题，正文与描述默认空串；格式仅支持 `md`、`mdx`，语言仅支持 `zh`、`en`。API 当前发布只强制描述非空，网页另行检查标题和正文，并在描述为空时从正文生成描述。目标服务端统一发布校验已在 Q26 确认，尚未实现。
- API 当前将 `publishedAt` 默认设为创建时刻，网页发布则改为发布时刻。网页发布按钮会切换发布状态，API 重复写入已发布状态仍会更新记录；不能直接把这些现状当作 CLI 独立发布命令的目标语义。
- 现有 PageHush 网页会创建、修改、发布/撤回及删除文章；这些调用尚未带版本条件或创建幂等键。相邻剪藏扩展的文章写入口只有 `POST /v1/articles` 创建草稿，未发现文章 PATCH/DELETE；其默认服务地址为 `https://pagehush.yohoia.cn`。目标兼容升级策略已在 Q19 确认，尚未实现。
- 现有博客 Markdown 的标题、描述、语言等来自 YAML frontmatter；两篇代表文章的正文都没有一级标题。现有 CLI 已依赖 `gray-matter`、`yaml` 和 `zod`，当前 `--body-file` 不提取 frontmatter，不能直接复用其输入语义作为新上传契约。
- 本地博客的代表文章包含 `../../assets/images/...` 图片引用，只有本地读取模式会把它们改为 `/media/`；远程读取不会转换这些本地路径。PageHush 创建文章仅保存正文字符串，上传 `.md` 不会自动上传关联图片或其他文档；现有 PageHush 素材 URL 则有对应的博客远程读取处理。
- PageHush 已有受认证保护的 `POST /v1/assets`，每次请求接收一个 JPEG、PNG 或 WebP 图片，单张最多 5 MiB；`kind=inline_image` 上传到服务器配置的存储适配器（生产使用 MinIO），返回稳定的 `/v1/assets/<uuid>/content` 地址。CLI 无需、也不应获得 MinIO 密钥。
- 当前素材上传每次产生新 UUID，没有按 checksum 去重；失败时的对象清理不完整，也没有素材删除接口。PageHush 博客能将素材 URL 改写为博客自己的图片代理地址，但仅接受有效文章引用且已就绪的资源。本轮已确认自动内嵌图片上传，需要为重试去重和无引用素材清理增加服务端能力。
- 剪藏扩展已有类似流程：将识别出的图片先上传 `/v1/assets`，再在内存中的文章正文替换 URL；正文图片上传失败会保留原图 URL 并继续创建文章。该流程存在重复资产和文章失败后遗留未引用素材的可能，不直接视为本 CLI 的目标行为。

## 授权方式调研

- GitHub CLI 官方文档提供浏览器登录、设备码交互和令牌输入，登录后优先使用系统凭据存储；环境变量令牌适用于无人值守运行。
- RFC 8628 的设备授权由 CLI 获取设备码，用户在浏览器确认，CLI 轮询授权结果并取得令牌，不需要本机回调端口。
- RFC 8252 描述原生客户端经外部浏览器授权、使用 PKCE，并可通过回环地址接收授权回调。
- PAT 由服务端签发，用户可将令牌用于 CLI；权限和有效期需要服务端控制。当前 PageHush 未提供该管理能力。
- 上述资料用于解释选项，不代表本项目已实现这些授权方式。用户已确认设备授权及后端改造方向，尚未进入实现。
